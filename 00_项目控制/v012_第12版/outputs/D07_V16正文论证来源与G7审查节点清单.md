# D07：V16 正文论证、来源与 G7 审查节点清单

**状态：** verified（依据 V16 正文生成/提交函数、V14 既有 G7、V15 输入结构、v007 分派和既有测试完成节点映射；本项为文档任务，不新增写作或审查门禁）。

## 一、节点定位：V16 是定性正文的 Chat/Codex 交接器

V16 `ai_writer4.py` 明确定位为 Chat/Codex hand-off interface，不是模型 API，也不是独立学术审查来源。其定性路径接受 V15 输入结构，生成逐节起草任务，接收真实正文与主张证据台账，执行本地结构/来源 ID/语言规则检查，再生成 G7 审查请求。

V16 仅服务 `secondary_interviews` 和 `online_qualitative`。定量输入明确返回原 main/V14 `stage07.py` 路径，不得切换到 V16。v007 的 `--writer4` 是显式 opt-in 的开发模式分派；formal 模式拒绝该参数，不能将 V16 视为已替换生产写作器。

## 二、输入与语言资源锁定

### 2.1 V15 输入结构

V16 的 `validate_packet()` 调用 V15 `writing_plan.render()`，复用核心研究问题、回答策略、方法路径、理论框架、案例设计、来源 ID 与定位，以及 problem、framework、case、理论维度、conclusion 的章节结构和每节论证任务。V16 不重新设计定性论文结构，也不执行定量的变量—模型—回归写作。

### 2.2 语言资源

`language_resources()` 读取并锁定：
- 03/v005 的 style profile、resource snapshot、15 项风格规则和 52 个功能单元；
- 03/v003 论证手册；
- 07/v014 文字要求；
- V16 定性章节风格映射。

函数核对已发布资源的 SHA-256，检查 15 个规则 ID、52 个功能单元与章节映射引用有效，并将资源路径与哈希写入 writer manifest。该步骤证明“本次使用的是锁定的资源文件”，不代表资源已通过正式业务审查。

当前 03/v005 `resource_snapshot.json` 的状态为 `needs_review`，`resource_available_for_formal_writing=false`。V16 因此只能标注实验使用，不得自动把风格资源提升为正式写作资源。

## 三、逐节任务生成：`prepare()`

默认 `mode="exploratory"`。程序拒绝覆盖已有 workspace，并按 V15 每个 chapter/section 生成独立的 `tasks/<task_id>.json`。每个任务绑定章节与分节 ID、标题、具体任务、论证和证据用途、当前节 source IDs 与来源对象、定性章节角色、v005 风格功能单元、ST 规则、v003 论证审查点，以及禁止虚构事件、引语、频数、受访者结局和独立核验的明确指令。

同时调用 V15 `render()` 生成 `writing_plan_v15.md`，并写入 `writer_manifest.json`：packet SHA-256、来源映射、章节与任务 ID、V15 写作方案 SHA-256、语言资源路径与 SHA-256、language profile 版本与当前 G3 资源状态，以及 `formal_eligible=false`、`independent_review_verified=false`、`stage="awaiting_draft"`、`full_paper_status="exploratory_only"`。

**V15→V16 的实际边界：** V16 复用同一 V15 packet 并重新调用 `render()`；没有读取或要求 V15 的 `writing_plan_review_request.json` 已通过。D06 所述 V15 审查结果当前没有接入 V16 的前置状态机，故“结构相同”不等于“V15 已独立审查通过”。

## 四、正文与主张证据台账：`review_draft()`

### 4.1 输入快照检查

提交时重新读取 packet、语言资源和 writer manifest，检查 packet SHA 与 prepare 时一致、语言资源锁一致、章节 ID 未变化、workspace 为 exploratory 模式，并能读取正文与主张台账。输入变化或结构不符时返回 `technical_revisions_needed`，不伪造学术通过。

### 4.2 当前主张台账合同

claims 文件必须有非空 claims 数组。每条 claim 检查：
- `claim_id` 非空且唯一；
- `exact_text`（或 `claim_text`）是字符串，且精确出现在正文；
- `source_ids` 是非空列表，且全部存在于 V15 packet 的来源映射。

此外检查正文二级标题数量与 V15 章节数量一致；若任务要求 2500 字符保守上限，则检查正文中文字符数。输出 `manuscript_sha256`、`claim_ledger_sha256`、`packet_sha256`，绑定本次稿件和主张台账。

**当前局限：** V16 的主张台账比 V14 定量 G7 的 claim schema 简化。它没有逐条要求 claim_type、evidence ID、result ID、reference ID、scope limit、paragraph ID、引用标记或来源文件哈希；也不判断来源正文是否真正支持该主张。精确文本出现且 source ID 存在，只证明“主张可定位并声明了来源”，不是语义证据核验。

### 4.3 语言与技术预检

V16 调用 V14 `language07.style_findings()` 生成确定性风格问题，写入 `style_review.json`，并明确 `human_language_review="pending"`。该检查只覆盖若干规则匹配与作者姓名引用格式，不证明论证充分、引文真实或事实无误。

## 五、V16 当前 G7 请求，不是 G7 通过

`review_draft()` 写入 `writing_review_request.json`，字段包括正文、claim ledger、packet 的 SHA-256，风格问题数量与结构错误，`gate="G7"`、`formal_pass=False`、`independent_review="pending"`，状态为 `technical_revisions_needed` 或 `exploratory_draft_awaiting_review`，并明确范围为单模型技术/风格检查而非科学批准。

**当前 V16 没有 G7 审查结果接收函数。** `submit` 命令实际调用的是 `review_draft()`，只做技术/语言预检并生成待审请求；没有审查者身份、审查意见、decision schema、审查报告 hash、pass/revise 状态机、返修接收或最终放行接口。即使预检没有结构错误，状态也只是 `exploratory_draft_awaiting_review`，`formal_pass` 仍为 false。

## 六、V14 既有 G7：可作结构参考，但不能冒充 V16 的定性 G7

### 6.1 V14 stage07 的原有验收链

V14 `stage07.py` 是原定量生产路径的 G7。它从冻结的 04/05/06 证据包、写作架构和段落计划生成任务，并对每稿执行：
- `manuscript07.audit()`：核对论文结构、摘要/正文长度、参考文献、主张定位、claim type、证据/结果 ID、引用标记和统计数字；
- 定量数字与锁定结果逐项复算，摘要、实证结果和结论需绑定实际结果；
- 逐项检查架构自检表，要求每项有通过状态与依据；
- `check_paragraphs()`：核对段落计划、段落用途、来源与主张；
- `language07.style_findings()`：生成确定性语言规则问题；
- `runtime.signoff()`：要求 review 的 decision 为 accepted、content_sha256 与本稿审核对象一致，并有 reviewer、reviewed_at 和 assessment。

G7 报告的状态按错误与输入是否变化分为 `passed`、`needs_review`、`stale` 或 `failed`；`business_quality_automatic=False`。只有当前有效 attempt 的 gate report 通过，才允许 export；export 仍写明 `submission_enabled=False`。

### 6.2 V14 signoff 的真实性边界

V14 `runtime.signoff()` 只验证审查决定为 accepted、审查对象 content hash 一致、reviewer 字段非空、reviewed_at 是有效日期、assessment 非空。它不核验 reviewer 是否为真实独立审查者，也不核验独立 thread/session、原始事件/响应哈希或审查者身份。V14 测试通过写入一个非空的测试 reviewer 名称、日期、assessment 和匹配 hash，即可模拟 signoff。故 V14 旧 G7 的字段合同也不能代替 D14–D20 的真实独立凭证。

### 6.3 V14 与 V16 的隔离

V16 只导入 V14 的 `language07.style_findings()`，没有调用 V14 `stage07.py`、`manuscript07.audit()`、`check_paragraphs()` 或 `runtime.signoff()`。V14 G7 的输入包、证据 ID、定量结果与三稿状态机不适用于直接验收 V16 定性稿。应复用其“冻结证据—主张台账—逐段核验—独立审查—通过后交付”的原则，不能把旧定量 G7 直接挂到 V16 上冒充已接通。

## 七、正式模式与生产分派边界

V16 `formal_gates()` 要求 packet 的 gate_status 同时具备：
- `independent_review_verified`
- `strict_literature_complete`
- `empirical_mechanism_verified`
- `formally_frozen`
- `independent_writing_approval`

还要求 03/v005 resource snapshot 为 passed 且允许正式写作。但即使上述标志都填 true，函数仍明确抛出错误：正式写作需要 separately verified upstream receipts，不能由 JSON flags 授权 G7。当前 G3 状态本身也为 `needs_review`，因此 formal 入口确实阻断。

v007 `run_mode.py` 的 `--writer4` 只在已存在且合规的 dev run 中显式分派；formal 模式拒绝 writer4。定量仍路由原 main/V14 `stage07.py`。这保持了生产隔离，但也意味着 V16 当前只是一条可实验的定性起草支路。

## 九、当前缺口与后续任务归属

1. **V15→V16 审查状态接续：** 需要让 V16 消费可验证的 V15 审查报告或明确的实验性例外，不能只复用 render 结构。
2. **主张—证据台账：** 需要逐条绑定正文位置、claim type、来源/材料 ID、原文定位、scope limit、支持与反例；验证来源正文是否支持主张，而非只检查 source ID 存在。
3. **段落/章节审查：** 需要记录每段的论证任务、证据用途、承接关系和具体审查意见，并绑定正文快照。
4. **G7 独立审查接收：** 需要真实审查 thread/session、审查者身份、输入快照 hash、原始 events/response 和结果报告 hash；无法核验时 unable_to_review 并阻断。
5. **返修闭环：** technical revisions 与 academic revisions 分流；每次返修绑定前稿 hash、审查 issue、修改稿 hash，复审通过前不能替换为正式版本。
6. **正式资格：** G3 语言资源、上游研究审查、严格文献与经验机制证据、冻结状态和独立写作审批全部有真实凭证后，才可解除 formal gate。

以上属于 D09–D20 的统一审查合同和凭证工作；D07 只记录 V16 当前实现与缺口，不在本项新增门禁或把旧 G7 强行接入。

**结论：D07 verified（节点映射完成，不代表 V16 G7 已实现）。V16 已实现定性逐节任务、资源哈希锁、正文与主张台账技术预检及 G7 待审请求；真正的独立 G7 审查、结果接收、返修和正式放行仍未完成。下一任务为 D08。**
