## 二、初始材料采集与框架定向材料搜索

### 1. 两个搜索区分别限额

`06_数据方法与分析/v005_第5版/tools/qual_materials.py`：
- `--framework` 或 `--matrix` 路径进入 `qualitative_framework`；初始转换搜索进入 `qualitative`。
- 两个区域各自检查本区域已有 `attempt_NNN` 目录；开发预算取 `manifest["workload"]["11"]`。
- 当前 `00_项目控制/v007_第7版/dev_profile.json` 的模块 11 为 `max_batches=1`、`native_search_actions=24`、`timeout_seconds=480`。所以初始材料搜索区与框架定向采集区各最多一个实际批次，不应相加成同一区域的两批预算。
- `read_materials()` 要求真实原生网页搜索事件存在且不超过 24；超预算或没有回执拒绝生成正常材料回执。
- 批次使用统计特意豁免“登录状态明确为 false 且没有 events.jsonl”的纯登录预检失败；登录成功、已出现搜索事件或没有可核验登录失败记录的目录会计入批次。实际 CLI 失败后写入 `search_incomplete` 并抛错，不能当成成功材料采集。

### 2. 框架文件修订不是材料补查或学术返修

同一 `qualitative_framework/attempt_NNN` 下，`--framework-revision` 在已有 `analysis_matrix_*.json` 达到 2 个时拒绝继续。修订还必须绑定原 `framework_sha256`、写明理由，并保持 `core_question` 不变；矩阵按新框架哈希另存，原文件不覆盖。

这是**每个 attempt 最多两个额外框架／矩阵修订产物**的文件版本限制；它不等于材料修复两批，也不等于独立审查允许两次实质返修。

## 三、材料定向整改批次：固定上限 2

权威常量位于 `06_数据方法与分析/v005_第5版/tools/repair_materials.py`：

- `REPAIR_BATCH_LIMIT = 2`。
- `revision_routes.preflight()` 通过 `directory.parent.glob("repair_*")` 统计已存在的修复目录；目录数达到上限时，source/event/framework 方向的定向修复返回 `resource_limit`。
- `repair()` 只接受已路由的独立审查缺口，创建 `qualitative_framework/repair_001`、`repair_002`；请求绑定父材料回执 SHA、审查问题及框架哈希。
- 修复提示要求只核查独立审查指出的缺口、优先打开一手来源、定位原文段落、区分来源主张和推论、每条一项离散事件、不把转载当独立事件；每项要标明原审查 `issue_index`。若替换旧记录，必须用 `supersedes` 指向父回执已有 material ID。
- 新旧材料按 ID 合并；被 supersede 的旧记录退役，新增记录及覆盖的问题索引写入子回执。父回执与历史原始文件不覆写。

**重要技术边界：** 同一请求只有在旧目录同时存在 `request.json` 和 `material_receipt.json` 时才会复用。若 CLI 在创建目录后失败、未生成材料回执，该目录仍被 `preflight` 和 `repair()` 的目录计数纳入；重试同一请求也不会复用这个不完整目录，而可能创建下一个批次。因此，**技术失败可能消耗两批材料整改预算之一**。当前源码没有“失败目录不计批次”或单独的修复技术重试配额。

## 四、实质性返修：矩阵与写作方案共享两次

权威入口为 `00_项目控制/v009_第9版/tools/resume_writing.py:resume()`：

1. `spent` 是共享返修计数。矩阵返修中，只要已路由问题包含 `fatal` 或 `substantial`，且该轮矩阵修改和完成性核验通过，`spent += 1`；纯 local 不增加此计数。
2. 进入下一轮时，若 `spent >= 2`，新的 fatal/substantial 问题被列入 `blocked_budget`，并在无其他可处理问题时以 `academic_stop` 停止。
3. 写作方案阶段使用 `for revision in range(3)`，即初稿加最多两次后续方案修订；每次 `revision > 0` 都使同一个 `spent += 1`。若矩阵阶段已消耗两次实质返修预算，写作方案阶段不能再进入第二版/第三版修订；若矩阵阶段未消耗，方案阶段最多消耗两次。
4. 方案每轮另有独立 review 派发；只有 review 的 `pass` 或 `stop` 才立即结束，否则继续下一版或在预算耗尽后 `academic_stop`。技术失败不等于学术返修通过。

因此不能把规则简化成“矩阵两次、写作方案再两次”。它是跨矩阵和方案阶段的**共享两次实质性返修预算**。

## 五、局部返修：最多两轮，但累计计数未持久化

- `technical_review.local_matrix_context()` 只有在所有检查项均为 `origin=analysis` 且 `severity=local`、并且每条意见能指向已有矩阵维度 ID 时，才构造局部上下文。
- 局部派发只提供被点名的维度及其材料；返回结果只能替换这些维度，其他矩阵行由原矩阵保留。若混入 source/event/framework/binding 或非 local 项，则不能走这一严格局部上下文。
- `resume()` 初始化 `local_rounds=0`；每完成一轮包含 local 项的矩阵修订，`local_rounds += 1`。当计数达到 2，且下一轮所有适用意见都是 local 时，返回 `local_revision_limit`。
- **持久化缺口：** `revision_checkpoint.json` 和恢复分支会恢复 `spent`，但没有保存或恢复 `local_rounds`；`autonomous_writing_status.json` 的 `local_revision_limit` 结果也没有写入该计数。重新调用 `resume()` 时，`local_rounds` 又从 0 开始。故“两轮”目前只能确认是单次进程调用内的限制，不能认定为整个 run 的累计硬上限。
- 另一个精确边界：达到两轮后，代码只拒绝“下一轮全部为 local”的请求；若下一轮是混合 local 与 substantial，判断条件不成立，仍可能进入后续预算判断。不能把它描述为“任何形式的第三轮局部意见一律拒绝”。

## 六、技术失败与技术重试：分入口登记，不混入学术返修

### 1. 写作恢复器的 CLI 技术失败

`resume_writing.dispatch()` 为每个派发标签创建 `attempt_NNN`。只有已存在且请求完全相同的 `validated.json` 才复用；失败目录没有 validated 结果时，后续调用会增加 attempt 编号并重新执行。单次 CLI 超时为 480 秒。主入口捕获 OSError/ValueError/KeyError/TypeError/RuntimeError/TimeoutExpired 后写入 `technical_block` 并重新抛出。

该路径没有发现每个标签、每个 run 或全局的技术重试次数上限；也未发现它调用 `run_mode.enforce()` 来执行 dev profile 的 module 07/08 预算。不能用 `spent` 学术返修数替代技术 attempt 数。

### 2. 原 v009 选题审查的 technical outcome

`staged_topic.route(history, "technical")` 返回 `retry_technical`；`review()` 将报告加入 history，但在结果为 `retry_technical` 时不推进状态。所核函数没有独立技术重试计数或上限。它与矩阵返修的 `spent` 不是同一计数器。

### 3. v012 autopilot 的全局调用预算是另一层

`00_项目控制/v012_第12版/tools/autopilot_v3.py:Executor.call()` 从 dev profile 读取 `00.model_calls=6`。它在调用 Codex 前先把 `started` 记录写入 ledger；失败后改记 `technical_block`，不会删除该条记录。因此真实 CLI 技术失败也会消耗全局 6 次调用额度。这个全局预算只适用于该 autopilot Executor；它不是 `resume_writing.dispatch()` 的技术重试上限，也不能证明写作恢复器已被同一额度约束。`--max-steps` 控制一次 autopilot 循环步数，不是某一阶段的失败重试次数。

### 4. 可自动关闭的纯制品技术问题

`technical_review.close_binding_review()` 仅在独立审查的所有变更都属于可确定核验的哈希/制品绑定问题、引用哈希能在真实 artifact lineage 中找到、matrix/receipt binding 一致时才返回修订矩阵。该路径记录 `model_calls=0`，不增加 academic revisions；它不是学术返修，也不是允许把理论、机制、案例或结论问题标记为技术问题的通道。

## 八、B11 验收结论

**B11：verified（静态源码与预算映射），但存在明确 not_verified 执行缺口。** 已定位：
- 初始材料搜索的一批/24 动作/480 秒限制与登录预检豁免；
- 两批材料定向修复、父子回执、supersedes、问题索引与失败目录计数；
- 每 attempt 两个框架/矩阵修订产物上限；
- 矩阵实质返修和写作方案返修共享两次计数；
- 单次调用内两轮 local 限制、维度级局部上下文及其跨调用计数丢失；
- topic technical outcome、写作恢复器 attempt 递增和 autopilot 全局六次调用额度的不同边界；
- 纯制品绑定修复不增加学术返修次数。

**未做：** 未改代码/配置、未重置或补跑任何材料、未运行 Codex、未进行独立审查、未真实触发技术重试、未验证返修成功率。发现的计数持久化和技术重试上限问题只登记，不在本任务擅自设计或放宽预算；后续如需修复，须另行授权并保持原学术门禁。
