## 0. 阅读口径与源码依赖

### 0.1 状态、动作、采集结果的区分

- 唯一顶层研究状态保存在运行目录的 staged_topic.json 顶层 status 字段。
- history 是独立审查记录列表；latest_search、stop_decision、budget_resume、autonomous_steps 是控制器附加状态字段，不是新的顶层状态。

- abstract_collection.json 的 bundle.status、checkpoint.json 中的 batch.status 也不是顶层研究状态。
- 本文中的“阶段通过”仅指源码满足进入下一状态的条件，不等于研究问题已经获得经验支持。

## 1. B02a：初始化与现实观察

**状态：** verified（静态源码核对）  
**源码：** staged_topic.py:L81-L110、L400-L419、L486-L513、L547-L549；run_mode.py:L15-L79；abstract_acquisition.py:L215-L227。

### 1.1 初始化输入与校验

| 输入 | 来源 | 校验/处理 | 输出 |
|---|---|---|---|
| run_id | CLI 必需位置参数 | dev 模式由 run_mode.start() 校验字母数字/下划线/连字符格式，长度 1–64；formal 分支在 init() 内执行同类正则校验 | 运行目录名 |
| mode | CLI --mode，默认 dev | 仅 dev/formal；dev 进入 run_mode.start() 和 verified_run()；formal 使用 runs_candidate 命名空间 | staged_topic.json.mode |
| theme | CLI --theme | main() 对 init 强制要求非空；本函数没有进一步做主题语义校验 | staged_topic.json.theme；dev run_manifest.json.theme |
| full_paper | CLI --full-paper | main() 只允许 init 且 mode=dev；写入 dev manifest 的 writing_policy；不改变研究阶段门禁 | writing_policy / writing_policy_sha256 |

dev 初始化：
1. run_mode.start() 读取 v007 dev_profile.json 和 v005 module_registry.json，要求 profile 覆盖全部已登记 module_id。
2. 创建 runs_dev/run_id，目录必须不存在；生成 run_manifest.json，包含 run_id、theme、run_mode=dev、formal_eligible=false、scope=experimental、workload、workload_sha256、registry_sha256、各模块 stages 及 writing_policy。
3. run_mode.verified_run() 重新核对运行目录父路径、run_id、run_mode、formal_eligible、workload 哈希、当前/兼容旧版 dev profile、生产 registry 哈希和 writing_policy。
4. staged_topic.init() 额外要求 sum(POLICY["dev"].values()) 等于 manifest.workload["04"]["abstract_target"]；不一致即失败。

formal 候选初始化：
1. 运行目录为 v009 版本目录下的 runs_candidate/run_id。
2. run_id 正则校验通过后以 exist_ok=False 创建目录。
3. 该分支不调用 dev run manifest；不因此获得生产资格。

两种模式随后均创建 staged_topic.json，初始字段至少包括：
- run_id、mode、theme；
- policy_sha256；
- history=[]；
- status=reality；
- formal_eligible=false；
- reality_first=true、method_paths=true、qual_search_receipts=true、explanation_first=true、issue_search=true。

### 1.2 现实观察输入、输出与状态推进

| 项目 | 具体合同 |
|---|---|
| 输入文件/参数 | CLI --report 指向的现实观察 JSON packet |
| 前置状态 | staged_topic.json.status 必须为 reality |
| packet 必需字段 | phenomenon、search_focus、sources 均为真值；sources 中每项必须包含 url、kind、supports、limits |
| 校验边界 | record_reality() 只检查上述字段是否存在/非空；该函数本身不校验 URL 是否 HTTPS、不核实来源真实性，也不评估来源是否足以支撑结论 |
| 落盘输出 | 运行目录/reality.json |
| 状态字段 | staged_topic.json.reality_sha256=digest(packet) |
| 默认下一状态 | explanation_first=true 时进入 explanation_exchange；否则进入 initial |
| 再读取 | load_reality() 重新读取 reality.json，并核对其 digest 与 state.reality_sha256 一致 |

main() 在 job_lock(work) 中读取状态、校验策略哈希/mode/run_id；命令成功后把状态写回 staged_topic.json。job_lock() 使用运行目录下 .lock 文件及 Windows msvcrt / POSIX fcntl 非阻塞 OS 锁，锁由文件句柄生命周期释放。

### 1.3 失败与退出条件

- run_id 不合法、目录已存在、dev workload 与模块 04 abstract_target 不一致、manifest 或 registry 哈希变化：初始化失败。
- 现实观察不是 reality 状态、packet 缺少现象/检索焦点/来源、来源缺少 url/kind/supports/limits：拒绝写入。
- reality.json 与 state 哈希不一致：load_reality() 拒绝继续。
- 现实观察记录成功本身不代表解释已成立；默认只把控制权交给 explanation_exchange。

### 1.4 本子项结论

初始化创建运行合同与顶层状态；现实观察创建 reality.json 并绑定哈希。现实来源的真实性和材料充分性不是 record_reality() 的职责，后续独立审查仍须判断。未运行 CLI 或真实材料收集。

## 2. B02b：解释反诘与议题定位

**状态：** verified（静态源码核对）  
**源码：** staged_topic.py:L105-L127、L526-L542；event_protocol.py:L17-L50；B01 CLI 表。

### 2.1 解释反诘输入与校验

exchange 命令只允许在 status=explanation_exchange 时执行。报告从 --report JSON 读取，并交给 event_protocol.validate_exchange()：

| 字段 | 要求 |
|---|---|
| expectation | 非空字符串 |
| observation | 非空字符串 |
| initial_explanation | 非空字符串 |
| challenge | 非空字符串 |
| candidate_question | 非空字符串 |
| research_actor / critical_actor | 均须为真值，且两者不能相同 |
| critical_receipt | 必须为真值 |

validate_exchange() 不解析 critical_receipt 的内部结构，也不单独验证参与者身份的外部真实性；它只校验上述字段和角色区分。不能仅凭 JSON 中填写不同 actor 名称就把真实独立审查验收为通过。

### 2.2 事件比较前置材料

当 state.issue_search=true（当前 init 默认值）时，exchange 分支还读取运行目录/event_comparison.json，要求：
- event_count 至少为 2；
- event_comparison.reality_sha256 与 state.reality_sha256 一致。

event_comparison.json 由 event_protocol.py 的 compare_events() 路径另行生成：逐事件检查 identity 不重复；事实项要求 statement、use、布尔型 key；source_id 必须能在 sources 中找到且来源 URL 为 HTTPS；status 只能是 corroborated、single_account、unverified、contradicted、inference。输出包括 events、event_count、sensitivity、interpretation_status=pending_independent_review、run_id、input_sha256、exchange_sha256、reality_sha256、formal_eligible=false。该文件不是 staged_topic.py 的 exchange 命令自动生成的。

### 2.3 exchange 落盘和状态变化

1. 要求 packet.search_focus 为非空字符串。
2. 写入 explanation_exchange.json。
3. 写入 state.exchange_sha256=digest(packet)。
4. 若 issue_search=true，另写 state.event_comparison_sha256=digest(comparison)。
5. 状态进入 issue_positioning；若 issue_search=false 则直接进入 initial。

### 2.4 议题定位方案

issue_plan() 读取 issue_plan.json，并要求其 digest 与 state.issue_plan_sha256 一致。

record_issue_plan() 要求当前状态 issue_positioning；以下字段必须是非空字符串：
- issue
- why
- object_search
- issue_search
- theory_search

specialist_journals 为可选列表；若提供，每行必须含非空 name、publisher_url、standing、fit；publisher_url 必须以 https:// 开头；名称不得与 POLICY.journals 或同一方案中已有名称重复。

成功后写入 issue_plan.json，state.issue_plan_sha256=digest(plan)，status=initial。

### 2.5 失败与退出条件

- 状态不符、反诘字段缺失、两个 actor 相同或 critical_receipt 为空：拒绝 exchange。
- issue_search=true 时事件比较文件缺失、少于两个事件、或 reality 哈希不一致：拒绝生成候选问题。
- search_focus 为空：拒绝写入 exchange。
- 议题字段不全、专业刊缺出版方 HTTPS/地位/适配性或重复：拒绝写入 issue_plan。
- issue_plan 文件被修改：后续 issue_plan() 哈希核验失败。
- 成功后才进入 initial；该状态变化不等于文献检索已经开始。

## 3. B02c：初查与理论材料

**状态：** verified（静态源码核对）  
**源码：** staged_topic.py:L100-L103、L129-L220；codex_literature.py:L16-L142、L143-L210、L211-L361；native_receiving.py:L1-L65；collect_common.py:L15-L46。

### 3.1 初查前置与配置

- 仅当 state.status=initial 时允许 search(phase="initial")。
- 读取 search_policy.json：初查目标 dev/formal 均为 5；期刊表为固定 9 刊。
- dev 模式调用 run_mode.verified_run()，从 manifest.workload["11"] 取得预算；配置 max_batches 使用 dev_profile["11"]["topic_batches_per_phase"]=3，timeout_seconds 使用 480，search_action_budget 使用 24，并写入 workload_sha256、run_mode=dev、topic_batch_budget=true。
- formal 模式没有 dev manifest 预算；search_policy.formal.initial=5，默认 max_batches=3、timeout_seconds=720。
- 有现实优先标志时，主题附加 reality.search_focus；有解释优先标志时，读取 explanation_exchange.json 并核验 exchange_sha256，附加其 search_focus。
- 若 issue_search=true，则读取并核验 issue_plan；期刊表追加 specialist_journals，search_guidance 包含议题方案和 exchange.candidate_question，检索主题改为 state.question（若无 question 则回退 theme）。
- 初查配置包含 theme、target、topic_search_phase、journals、max_batches、timeout_seconds、excluded_titles（初查为空）；dev 另含预算字段。
- collector 还接收 v009 search_prompt.txt 与由 native_library.registry() 定位的 native_response.schema.json。

### 3.2 采集器调用及其直接 I/O

staged_topic.search() 调用 codex_literature.collect(config, folder, prompt, schema, resume=...)。其主要合同：
1. 校验 phase 对应 target：initial=5；主题长度 2–160；max_batches 1–8；timeout 60–1800 秒。
2. 以 ENGINE、config、prompt/schema 文件哈希和 collector 源码哈希生成 config_sha256。
3. 新建 checkpoint.json，记录 config_sha256、collection_id、engine、config、batches、observations、rejected；resume 时要求 checkpoint 存在且配置/身份匹配，预算迁移须满足单独的旧 checkpoint 哈希条件。
4. 每个批次建立 batch_NNN 目录，保存 prompt.txt、login_diagnostics.json、login_status.json、events.jsonl、stderr.log、response.json；登录探测必须确认 ChatGPT 登录，执行器以只读、临时会话、原生搜索方式运行，不传 API key。
5. evidence() 只接纳 web_search 类型事件；若出现 command_execution、mcp_tool_call 或 file_change，拒绝该批次作为原生网页搜索证据。
6. observation() 要求期刊在许可列表、标题可规范化、作者非空、年份 1900–2100、相关性 direct/substantive 且理由非空、摘要总结非空、摘要摘录长度 8–90 且有 locator；metadata_url 和 abstract_url 都必须能关联到原生搜索事件。
7. group() 按 DOI 或同刊同题同年身份规则合并观察；冲突/歧义记录被排除，保留 provenance。
8. 每批完成后更新 checkpoint.json；最终写 abstract_collection.json，包含 engine、schema_version=2、acquisition_mode=abstract_only、collection_id、theme、journals、target、count、articles、conflicts、batches、unverified、status。dev 另写 run_mode、formal_eligible=false、workload_sha256；动作超预算时 status=experimental_budget_exceeded。

### 3.3 接收复核与矩阵

receipt(folder,journals) 调用 native_receiving.receive()，再读取 checkpoint.json。receive()：
- 读取 checkpoint.json 和 abstract_collection.json；
- 核验 engine、schema_version=2、journals、collection_id；
- 对每个 completed batch 核验 events.jsonl/response.json 哈希及 login_status.json 必须等于 {"chatgpt": true}；
- 根据 checkpoint observations 重建 observation 并与原记录逐项比较；
- 重新执行 group()，要求 articles、conflicts、count 与 bundle 一致；
- 从原生搜索结果 snippet 检查 abstract_excerpt 是否可见；
- 写 literature_matrix.json，记录 schema_version=2、mode=abstract_only、collection_id、collection_sha256、theme、journals、verified_rows、excerpt_visible_count、rows、conflicts；dev 另写 run_mode、formal_eligible=false、workload_sha256。

注意：verified_rows 是接收器按回执重建的有效题录数，不等于摘要摘录一定在搜索结果中可见；excerpt_visible_count 是单独字段。矩阵的 analysis_status 初始为 not_analyzed，不代表论文已经精读。

### 3.4 理论材料与进入初步审查

theories() 只检查 completed 批次的 notes；每条备注须可拆为 THEORY|title|url|claim 四段，且 url_event() 能将 URL 绑定到对应原生 web_search 事件，title/claim 非空。search() 将结果写入 initial/theories.json。

初查通过门槛：
- matrix.verified_rows >= POLICY[mode].initial（5）；
- theories.json 非空；
- bundle.status != experimental_budget_exceeded。

满足后 state.status=preliminary_review；否则维持 initial。无理论证据时即使摘要数达标，也不会进入初步审查。每次 search 都更新 state.latest_search（phase、verified_count、collection_sha256）。

若 issue_search=true，还会在初查目录写 journal_tiers.json，区分 core_nine 与 specialist 期刊的 article_id。

### 3.5 停止条件

Codex CLI 不存在、ChatGPT 登录失败、超时、无原生 web_search 回执、摘要/题录校验失败或采集器预算超限，均不能被当作有效文献通过。具体技术失败由采集批次 checkpoint 留痕；阶段状态是否停止由 advance() 处理（见 B02e）。

## 4. B02d：补查与跨阶段合并

**状态：** verified（静态源码核对）  
**源码：** staged_topic.py:L145-L220；codex_literature.py:L96-L142、L211-L361；native_receiving.py:L7-L65。

### 4.1 输入与初查复核

- 仅当 state.status=supplemental 时允许 search(phase="supplemental")。
- 首先读取 initial/literature_matrix.json；读取 issue_plan（如启用）并核验哈希。
- 期刊集合与初查保持一致；补查主题使用已审查 question/theme，并加补查标识；excluded_titles 来自初查矩阵，防止把已有题目原样重复提交。
- 重新执行 receipt(initial, journals)，要求初查矩阵 digest 与 state.initial_sha256 相同。
- 从初查有效 rows 前 POLICY[mode].initial 项的 provenance 中提取 observation_id，再回到初查 checkpoint.observations 取原始观察记录，作为 original_rows。
- 开发模式 topic_batch_budget=true 时将 original_rows 交给 collector，使补查批次按跨阶段去重后的新增量计算。

### 4.2 补查采集与合并

- 补查目标 dev=5、formal=35；初查+补查总目标 dev=10、formal=40。
- receive() 先写 supplemental/literature_matrix.json 并返回 checkpoint。
- 为避免两个独立 collector 重用 batch_NNN 产生 observation_id 冲突，补查 observation_id 加 supplemental: 前缀。
- group([original_rows, scoped_supplemental_rows]) 生成跨阶段 merged rows 和 conflicts；count=合并后有效论文数。
- 当 count 达到初查与补查目标总和，且 bundle.status 不为 experimental_budget_exceeded 时，写入 merged_literature.json，包含 rows、conflicts、initial_sha256、supplemental_sha256。
- 若达到门槛且预算状态正常，state.status=final_review；否则保持 supplemental。
- state.latest_search 更新 phase、verified_count、collection_sha256。

### 4.3 输出文件

补查目录 supplemental/：
- checkpoint.json：批次、观察、拒绝记录与配置；
- abstract_collection.json：补查采集器原始集合；
- batch_NNN/：原始执行回执；
- literature_matrix.json：接收器复核矩阵；
- journal_tiers.json：启用议题定位时写入；
- merged_literature.json：只在总目标达成且预算状态正常时写在运行目录根部。

### 4.4 退出条件与边界

- 初查矩阵哈希与审查后保存的 initial_sha256 不一致：拒绝补查，防止改写已审证据。
- 初查 provenance 无法回到 checkpoint observations：不能形成可核验的 original_rows。
- 采集器未达到补查有效量或总目标：不进入 final_review。
- 有预算超限：不写入有效的 merged_literature.json，也不推进 final_review。
- conflicts 会被保留用于审查，不可将合并数量直接等同于无冲突、可用于论证的独立研究数量。

## 5. B02e：预算判断、停止、续跑与恢复

**状态：** verified（静态源码核对）  
**源码：** staged_topic.py:L223-L313；codex_literature.py:L211-L361；run_mode.py:L63-L79。

### 5.1 literature_next() 的输入与决策

输入为 checkpoint、当前有效 count 和 target。它读取 checkpoint.config、batches、login_preflight_only_batches、max_batches、search_action_budget、topic_batch_budget。

| 条件 | 返回 action |
|---|---|
| count >= target | verify |
| count 未达且剩余批次为 0，或非 topic_batch_budget 模式下搜索动作预算耗尽 | stop |
| 目标未达且仍有批次/动作预算 | resume_deficit |

返回值同时记录 count、target、deficit、batch_limit、used_batches、remaining_batches、recorded_search_events、search_action_budget。被标记为 login_preflight_only_batches 的批次不计入有效批次。

### 5.2 advance() 的处理路径

1. 若顶层状态为 literature_budget_exhausted，读取 stop_decision 中的 phase，重载该阶段 checkpoint。
2. 只有 mode=dev，且 checkpoint.config.max_batches 仍低于 dev_profile.topic_batches_per_phase 上限，才可能恢复。
3. 重新 receive 文献矩阵，并要求 checkpoint digest 与 prior_stop.checkpoint_sha256、collection_sha256 与 prior_stop.collection_sha256 一致。
4. 一致时将状态恢复为 initial 或 supplemental，写 budget_resume（phase、prior_stop、new_batch_limit）；不满足则返回 already_stopped，保持停止状态。
5. 若当前顶层状态不是 initial/supplemental，返回 wait_for_stage_input，不擅自推进。
6. checkpoint 不存在时调用 search(..., resume=false)；formal 模式或 search 已改变顶层状态时返回该次结果。
7. dev 旧配置若缺少 topic_batch_budget，必须匹配先前停止记录中的 checkpoint 哈希，才允许预算迁移和 resume。
8. 读取 abstract_collection.json 并重新 receipt；补查且 latest_search 与当前 collection_sha256 一致时，将累计 count 减去初查目标，得到本轮补查量。
9. decision 附加 phase、origin、collection_id、collection_sha256、checkpoint_sha256。
10. 最近批次 failed 时动作覆盖为 retry_technical；bundle.status=experimental_budget_exceeded 时动作 stop、failure_kind=resource_limit，并写顶层 literature_budget_exhausted 与 stop_decision；目标达标但理论文件为空时返回 wait_for_theory_evidence；普通 stop 也写预算停止原因和 unverified_count。
11. resume_deficit 时调用 search(..., resume=true)；dev 且仍处在原阶段时追加 autonomous_steps、持久化 staged_topic.json，并递归调用 advance() 继续处理。

### 5.3 关键退出条件

- 目标达标是必要条件，但初查还必须有理论材料。
- 批次/搜索动作预算耗尽且目标未达，进入 literature_budget_exhausted。
- Codex 登录预检失败批次可被单独标记并从有效批次计数排除；不能把登录失败批次算成有效搜索批次。
- 预算恢复不是无条件重跑：仅开发模式、原 checkpoint 和文献集合哈希完全匹配、且批次额度确有可增加空间时才允许。
- retry_technical 是动作而非顶层状态；不得将其写成新的研究阶段。
- formal 模式不使用 dev 的自动递归续跑规则；advance() 的调用边界必须与实际状态、mode 一起判读。

## 6. B02f：独立审查、学术退回与归档

**状态：** verified（静态源码核对）  
**源码：** staged_topic.py:L44-L80、L314-L374、L420-L437；method_paths.py:L7-L100；abstract_acquisition.py:L215-L227。

### 6.1 审查输入与证据绑定

review() 只接受以下顶层状态：preliminary_review、design_review、final_review、materials_pending、S02、S03、S06、S05。

- final=true 的判定：status=final_review 或 review_phase=final。
- final 审查材料为 merged_literature.json；其他审查材料为 initial/literature_matrix.json。
- 理论材料固定为 initial/theories.json。
- evidence_hash() 对 papers、theories 计算哈希；按标志追加 reality、explanation_exchange、issue_plan、event_comparison，并对 reality/exchange/issue_plan/event_comparison 既有哈希逐项核验。
- 报告必须 model=gpt-6.2-sol、invocation_id 非空、evidence_sha256 与当前材料一致、reason/question 非空；history 中不得出现重复 invocation_id。

### 6.2 审查结果的共同门槛

- pass、academic_pass、missing_data、materials_pending 均要求 academic_value=pass。
- reality_first=true 且 outcome 为 pass/missing_data 时，research_case.core_question 必须等于 report.question，context 非空，hypotheses_or_propositions 为非空字符串列表。
- outcome=pass 还要求 data_feasibility=pass。
- outcome=missing_data 要求 data_feasibility=blocked，archive.run 与当前 run_id 一致，archive.question 与 report.question 一致。
- method_paths=true 且 outcome 为 pass/missing_data/materials_pending 时，必须提供 method_assessment，并完整评估 quantitative、secondary_interviews、online_qualitative 三条路径。

### 6.3 方法路径的校验

每条路径 status 只能为 ready、missing、unknown、not_applicable，且必须有非空 reason。
- ready：materials 为非空字符串列表，access=verified。
- online_qualitative：approach 只能 public_text 或 ethnography；ethnography 还要求 observation=verified。
- pass：selected 必须是 ready 路径，返回标准化 research_method。
- missing_data：selected 必须为空；所有适用路径都必须为 missing，不能把 unknown/not_applicable 误判为材料不可得。
- materials_pending：selected 必须为空，且至少一条路径为 unknown。
- qual_search_receipts=true 时，secondary_interviews 与 online_qualitative 的 missing/ready 判断还要绑定真实 qualitative/attempt_NNN/material_receipt.json、conversion.json、events.jsonl、response.json；核验 receipt 哈希、run_id、pending_independent_review 状态、tool_events、conversion 哈希、原始事件/答复哈希、问题复用说明和 material_id 归属。missing 还须 search_assessment=reasonable_but_insufficient。

### 6.4 状态路由与归档

| outcome / 路由 | 状态与落盘结果 |
|---|---|
| academic_pass | 仅限初步学术审查；追加 history、更新 question，进入 design_review 并提前返回 |
| pass（初查上下文） | 保存 research_method（若启用），进入 supplemental；写 initial_sha256 |
| pass（最终审查上下文） | 保存 research_method（若启用），进入 s08_ready |
| materials_pending | 进入 materials_pending，可再次提交审查，不等于通过 |
| concept / value / depth / increment | 分别映射 S02 / S03 / S06 / S05；route() 统计的是本次之前 history 中已有的学术失败数，若此前已至少两次则本次进入 eliminated |
| missing_data | 先校验归档合同并调用 archive()，再进入 archived |
| technical | 返回 retry_technical；report 仍追加 history、review_phase/question 更新，但顶层 status 保持原审查状态 |

archive() 要求 core、question、value、literature、missing、access、run、review 八项均为非空字符串。以 normalize(core)|normalize(question) 的 SHA-256 前 20 位生成去重 key；若库中已有 marker 则幂等返回，否则在潜在研究选题库.md 追加完整记录。该写入在 job_lock(library.parent) 下经临时文件替换完成，并把 key 写入 state.library_key。

### 6.5 失败与停止边界

- evidence_sha256 不匹配、报告缺 invocation/reason/question、重复 invocation：拒绝审查。
- 不能用 academic_value 以外的通过字段替代学术价值判断。
- 数据可行性未通过时不能 pass；只有所有适用方法路径均确认 missing 才能归档。
- unknown 表示尚待查证，进入 materials_pending，不得作为 missing。
- 技术重试不改变顶层状态，但审查记录会追加；重复提交相同 invocation_id 会被拦截。
- 本表只记录控制器如何接收独立审查报告，不证明报告来自真实独立会话；invocation_id 不能单独证明审查独立性。
