# D04：事件事实比较与解释反诘核验节点清单

**状态：** verified（依据原 v009、v012 对应函数和既有测试完成节点映射；本项为文档任务，不新增平行事实门禁）。

## 一、节点地图：四种核验不能混为一谈

D04 涉及四个相互衔接但职责不同的节点：

1. **现实线索来源核验（reality）**：确认现实观察中的来源能追溯到当前原生搜索记录；它只支持“发现了可观察线索”，不等于事件事实已核实。
2. **事件比较与事实级来源凭证（events / event_comparison）**：将来源 URL、原生搜索/打开事件、thread、原始响应和 events 哈希绑定；再将每条事实分为已核验来源支持或待核事实。
3. **研究者解释与反诘输入（research_exchange / critical_exchange）**：先形成研究者的预期、观察、初始解释和候选问题，再由不同原生 thread 的批评会话提出挑战和竞争解释。
4. **正式独立学术审查（preliminary_review / design_review / final_review）**：由原 v009 审查状态机另行处理。事件比较和批评者会话均不能自行授予学术审查通过。

## 二、现实线索核验：只能证明来源进入过当前搜索

原 v012 `autopilot_v3.py` 在 reality 阶段调用原生搜索，并将结果交给原 v009 `record_reality()`。现实来源必须包含 HTTPS URL；`source_proof()` 会检查 URL 有效，并确认该 URL 能匹配当前原生搜索 trace 中的事件。

原 v009 `record_reality()` 还要求每个来源记录 `kind`、`supports`、`limits`，并把现实材料写入 `reality.json`，保存 `reality_sha256`。后续加载现实材料时会重新核对哈希，避免研究中途静默替换。

**重要边界：** reality 阶段的 `source_proof()` 只核验来源能否匹配原生搜索事件；它本身没有要求对每个现实来源执行 `open_page/find_in_page`。因此现实线索来源进入过搜索结果，不应直接写成页面内容已核读或事件事实已核实。更严格的“搜索 + 打开”凭证在后续事件比较节点执行。

## 三、事件比较与核心事实核验：v009 `event_protocol.py`

### 3.1 输入与执行上下文

v012 要求事件比较任务：
- 至少比较两个可区分的真实事件；
- 为每个来源提供 source ID 到 HTTPS URL 的映射；
- 每个引用来源都要通过原生 `open_page/find_in_page` 打开，不能只依据搜索摘要；
- 每个事件列明唯一 identity 与事实；每条事实提供 `source_id`、`statement`、`use`、`key` 和可信度状态；
- 一个报道描述两个地点，不等于两份独立报道。

事件采集必须使用原生网页搜索。v012 将同一 attempt 的 `response.json` 和 `events.jsonl` 传给原 v009 `event_protocol.py`；协议拒绝两文件不属于同一 attempt 或路径逃出当前研究目录的情况。

### 3.2 来源凭证构建

`build_source_receipts()` 对每个 source ID 建立来源回执，至少核验：

1. source ID 非空；
2. URL 是无用户名/密码的有效 HTTPS，并按原 URL 规则规范化；
3. 当前 attempt 的 `response.json` 与 `events.jsonl` 都存在；
4. 能从当前原生 trace 找到该来源的搜索事件；
5. 能找到同 URL 的 `web_search` 原生事件，其 action 是 `open_page` 或 `find_in_page`，且包含结果；
6. 当前执行具有 `thread_id`；
7. 记录事件文件、响应文件的研究目录内相对路径与 SHA-256。

缺少来源、搜索事件、页面打开、原始文件或 thread 时，回执保留为 `pending`，并写明原因；不会因为模型在材料包中填写了 URL 就自动变成 verified。

### 3.3 当前执行与来源回执必须完全匹配

`compare_events()` 再把逐来源回执与当前 execution context 比较。只有同时满足下列条件，来源才保留 `verified`：

- source ID 与事实引用的 source ID 相同；
- 规范化 URL 一致；
- 事件类型为 `web_search`；
- `opened=True`，且 `event_id == open_event_id)；
- action 类型为 `open_page` 或 `find_in_page`；
- thread ID、events/response 路径与当前执行一致；
- events 和 response 的 SHA-256 格式正确且与当前执行完全相同。

未满足任一条件时，来源降为 `pending`；事实也被降为 `unverified`，原模型声明的状态另存为 `model_claimed_status`，并进入 `uncertain_facts`，不进入 `retained_facts`。

### 3.4 事实级分类

每条事实必须提供非空的 `statement`、`use`，以及布尔型 `key`；状态只能为：

| 状态 | 当前处理 |
|---|---|
| `corroborated` | 只有对应来源回执已 verified 时，才进入 `retained_facts` |
| `single_account` | 进入 `uncertain_facts`，不能当作已交叉印证 |
| `unverified` | 进入 `uncertain_facts` |
| `contradicted` | 进入 `uncertain_facts`，保留冲突 |
| `inference` | 进入 `uncertain_facts`，不能伪装成直接事实 |

所有 uncertain 中标记为关键事实的条目进入 `critical_gaps`。输出还包含 `pending_sources`、`pending_fact_count`、整体 `source_verification_status`，并固定为 `interpretation_status="pending_independent_review"`、`formal_eligible=False`。

**关键限制：来源凭证不等于语义证实。** 当前代码核验来源是否在原生搜索记录中、是否打开、是否与同一 thread/attempt/hash 匹配；它没有自动判断打开的页面正文是否真正支持该条事实，也没有对“corroborated”执行跨出版方/跨来源的语义独立性验证。事实状态仍由提交的材料包给出。故“来源已打开”只能证明来源链条完整，不能单凭这一点证明事实真实或已被多源独立印证。

## 四、事件数量与独立来源边界

- v012 的事件任务提示明确要求至少两个可区分的真实事件，并提醒不能把一篇报道中的两个地点冒充两份独立报道。
- 原 v009 `exchange` 命令在默认启用 `issue_search` 时要求 `event_count >= 2)，并核对 `event_comparison.reality_sha256` 与当前现实材料哈希一致。
- 但 `compare_events()` 本身只拒绝重复 identity，不负责证明两个事件具有不同的独立报道来源；也没有确定性规则核验出版方、作者或原始报道是否相互独立。
- 原 `exchange` 入口只检查事件数和现实快照哈希，不要求 `source_verification_status == "verified"`。因此有 pending 来源或事实时仍可能进入解释/反诘阶段，但 v012 给研究者的任务明确要求：只有 `retained_facts` 且 `source_verification_status="verified"` 的事实可作为已核实经验支持；`uncertain_facts`、`pending_sources` 和 pending 状态必须作为待补缺口，不能引用为既定事实。

所以事件比较产物是证据分层和待核问题清单，不是事件解释成立的裁决，也不是所有事实均已核实的证明。

## 五、解释与反诘：v009 结构合同和 v012 独立会话派发

### 5.1 原 v009 `validate_exchange()`

原始解释/反诘包必须提供：
- `expectation`：预期；
- `observation`：观察；
- `initial_explanation`：初始解释；
- `challenge`：反诘；
- `candidate_question`：形成的候选问题；
- `research_actor` 与 `critical_actor`：不同角色；
- 非空 `critical_receipt`。

若启用 `issue_search`，原 v009 还会核验事件比较数量至少为 2、比较材料属于当前 run 的现实快照，再保存 `explanation_exchange.json` 和 `exchange_sha256`。后续文献检索与审查会重新核验该快照。

**原 v009 单独的限制：** `validate_exchange()` 只检查 actor 字段不同、receipt 字段非空；它不会自行打开 `critical_receipt.json` 并验证真实 thread、events、response 哈希。因此，不能只凭 v009 收到一个非空字符串就宣称独立反诘凭证已经验真。

### 5.2 v012 `autopilot_v3.py` 的真实会话合同

v012 补充了执行器层的会话与原始凭证绑定：

1. `Executor.call()` 为每次调用保留 attempt，保存 task、response 和原始 events；从 `thread.started` 读取真实 thread ID，并记录 events/response SHA-256。需要搜索的阶段必须有原生搜索 provenance。
2. `completed_call()` 只复用状态为 completed、任务文本完全一致、原始 events/response 文件存在且哈希未变、events 中 thread ID 与 ledger 一致的历史调用；批评会话还排除与研究者 thread 相同的调用。
3. `saved_critical_input()` 只接受能解析出冻结 reality 和 event comparison 的既有任务；它们必须与当前 run 文件完全相同，并绑定当前 run ID 和 reality SHA。已有有效输入可续接，不应随意重做。
4. 批评任务明确要求新建独立批评会话，质疑研究者最强假设、反例和竞争解释；不允许同一会话角色扮演冒充独立证据。
5. 研究者与批评者 thread ID 相同会直接报错；批评者必须返回非空的实质 challenge。
6. 控制器写入 `critical_receipt.json`，绑定 run、stage、研究者/批评者 thread ID、各自 events/response 路径及哈希、批评任务哈希、保存的 critical input 路径/哈希，并记录 `thread_separation="verified_by_distinct_thread_ids"`。
7. `exchange_payload.json` 将批评内容、角色标识、receipt 路径和哈希交给原 v009 `exchange` 入口，不另建第二套研究状态机。

### 5.3 仍然不能混同的两种“独立”

- **独立反诘会话：** 当前 v012 通过不同真实 thread ID 与原始事件/响应哈希证明研究者调用和批评者调用是不同会话；两者仍可由同一 Codex 执行器/模型创建。
- **独立学术审查：** 对学术价值、设计和最终研究作出正式放行的独立审查，仍需 D14–D20 核验真实审查身份、会话来源和接收凭证。不同批评 thread 不等于独立学术审查者，也不产生 `academic_pass` 或 `final_review pass`。

## 六、节点状态与禁止事项

| 节点 | 通过/产物 | 不代表什么 |
|---|---|---|
| reality source proof | 来源 URL 与原生搜索事件匹配；现实材料哈希保存 | 不代表页面已打开或事实已核实 |
| event comparison | 来源回执、打开事件、thread/原始文件哈希绑定；事实分层；输出 pending gaps | 不代表页面语义已独立验证、事件间来源独立或解释成立 |
| explanation exchange | 预期—观察—初始解释—反诘—候选问题结构完整；现实/比较快照绑定 | 不代表反诘者是真实独立会话，除非 v012 receipt 也核验 |
| critical receipt | 研究者与批评者不同 thread，原始事件/响应哈希保存 | 不代表批评者具有独立学术审查身份或正式放行权限 |
| academic review | 进入原 v009 review 状态机并通过对应审查 | 不能由事件比较或批评者会话代替 |

不得把搜索结果摘要当作打开页面；不得把同一报道拆成多个事件以凑数量；不得把单一来源写成多源印证；不得把模型给出的 `corroborated` 状态当作自动语义核验；不得把同模型同 thread 自我扮演写成独立反诘；不得把反诘会话的 challenge 当作正式学术审查结论。

## 八、后续应保留的明确缺口

1. **来源语义核验：** 当前确定性逻辑证明“来源已搜索/打开且回执一致”，不证明网页正文语义支持事实。后续需以事实 ID、原文位置、支持范围、反证和独立来源完成语义审查。
2. **来源独立性：** 当前没有确定性 publisher/author/source independence 判定；“至少两事件、至少两份独立报道”目前主要来自任务提示和人工判断。
3. **v009 exchange receipt 验真：** 原 v009 仅检查 `critical_receipt` 非空；v012 有 receipt 生成逻辑，但原接收端未独立重算其路径与哈希。应在 D14–D20 凭证接收工作中补齐，不在 D04 新建平行门禁。
4. **真实执行：** FakeEngine 测试不能代替真实 CLI 的 thread.started、网页事件、response/events 文件与批评会话回执。真实运行任务仍按当前暂缓策略单独登记。
5. **正式学术审查：** 不论事件事实和批评会话如何完成，仍须通过 D01–D03 对应的原 v009 学术审查；不得在事件协议中直接生成审查通过状态。
