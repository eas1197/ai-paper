# B15｜文献检索入口与正式准入路径映射

**状态：verified（静态调用链与配置映射；不代表真实检索或端到端准入验收）。**  
**分支：** \`dev/v3.1-abstract-acquisition\`。  
**范围：** 仅核对原 v009/11-v007/04-v012 路径、04/v012 standalone candidate、v005 production registry→04/v008 路径及正式门禁。未运行搜索、未改配置、未改生产注册。

## 一、结论先行

仓库里存在三条容易混淆、但不能互相替代的路径：

1. **当前 5.0/v012 实际继承的原 3.x 路径：** v012 strict/autopilot 调用原 v009 状态机；v009 以自己的 \`search_policy.json\` 生成九刊任务，调用 11/v007 的 \`codex_literature.collect()\`，再调用 04/v012 的 \`native_receiving.receive()\` 做来源凭证和摘要矩阵接收。v012 strict 的 \`original_command()\` 固定传 \`--mode dev\`，所以当前 v012 走的是 v009 dev 配额（initial 5 + supplemental 5），不是 v009 formal 配额（5 + 35）。

2. **04/v012 standalone Codex candidate：** \`native_library.py --profile paper_codex_native\` 是独立的九刊、摘要级候选入口，manifest 状态为 \`candidate\`。按用户要求，两份模板为 \`target=0/max_batches=0\`，默认调用返回 \`disabled\`，不启动搜索、不调用采集/接收、不创建运行目录。它不是 v009 主流程，也不是正式文献准入入口。

3. **当前 v005 production registry 指向的旧 04 路径：** \`00/v005/module_registry.json\` 将模块04注册到 \`04/v008\`，入口为 \`04/v008/tools/research.py\`。该路径使用六刊范围、100篇摘要/25篇核心全文和 G4 全文/研究复核门槛；但 v008 manifest 的 \`business_status=planned\`，所以“在生产注册表中登记”不能写成“业务验收已通过”。

**核心边界：** 11/v007 是可复用的检索执行/凭证适配器，不决定某个入口的研究状态或正式准入。真正决定范围和放行的是调用它的控制器、接收器及后续门禁。04/v012 的九刊候选矩阵不能仅凭生成成功就视为 v009 review/S08 通过或 v008 G4 通过。

## 二、调用链逐条核对

### 1. 当前 5.0/v012 实际使用的原 3.x 路径

\`\`\`text
v012 strict / autopilot_v3
  └─ 原 v009 staged_topic.py（状态机与阶段控制）
       ├─ 读取 v009/search_policy.json（九刊；dev/formal 配额）
       ├─ 11/v007/tools/codex_literature.py
       │    └─ collect()：Codex CLI 搜索、events.jsonl、response.json、
       │       login_status、摘要题录观察与原始来源凭证
       └─ 04/v012/tools/native_receiving.py
            └─ receive()：核对原始事件/响应哈希、登录记录、观察重建、
               去重与 abstract_only literature_matrix
\`\`\`

源码证据：

- v009 \`staged_topic.py\` 的 \`sys.path\` 同时加入 11/v007、00/v008 和 04/v012 工具目录；随后从 \`codex_literature\` 导入 \`collect/evidence/group/url_event\`，从 \`native_receiving\` 导入 \`receive\`。其 \`search()\` 从 v009 \`POLICY\` 读取期刊与阶段数量，再调用 \`collect()\`；\`receipt()\` 调用 \`receive()\`。
- v012 \`ai_paper5_strict.py\` 的 \`original_command()\` 固定添加 \`--mode dev\`；\`status()\` 在 initial/supplemental 阶段转发给原 v009 命令。它没有把 04/v012 standalone CLI 作为新的文献状态机。
- v012 \`autopilot_v3.native_modules()\` 调用 \`native_library.registry()\` 主要用于建立原 11/v007/04/v012 模块路径，随后直接导入 11/v007 的 \`codex_literature\`；没有调用 \`native_library.main()\` 或 standalone CLI。

**因此：** 当前 v012 继承的是“原 v009 状态机 + 11/v007 collector + 04/v012 receiver”的组合，不是“调用 04/v012 standalone candidate”。同一个底层 collector 被复用，不意味着两种 orchestration/配额/准入相同。

### 2. 04/v012 standalone candidate 路径

\`\`\`text
04/v012/tools/native_library.py
  ├─ 读取 v3.1_Codex检索候选注册表
  ├─ 检查 profile=paper_codex_native、enabled_by_default=false
  ├─ 检查九刊与 v009/search_policy.json 完全一致
  ├─ 加载 11/v007 collector 与 04/v012 receiver
  └─ target=0,max_batches=0 → status=disabled 并立即退出
       （正数目标只允许显式独立候选运行；仍是摘要级候选）
\`\`\`

关键核验：

- \`04/v012/manifest.json\`：\`status=candidate\`、\`scope=native_search_abstract_only\`、\`profile=paper_codex_native\`、\`entrypoint=tools/native_library.py\`。
- \`v3.1_Codex检索候选注册表.json\`：\`enabled_by_default=false\`，模块指向 11/v007 与 04/v012，九刊名单与 v009 policy 一致。
- \`native_library.registry()\` 不只检查九刊数量，还要求 candidate journals 与 v009 policy 名单及顺序完全一致。
- \`native_library.main()\` 在 target 为零时，要求 max_batches 也为零；随后在导入 \`collect/receive\`、创建运行目录之前返回 \`disabled\`。两份模板当前都为零目标。
- \`native_receiving.receive()\` 生成的是 \`mode=abstract_only\` 的摘要矩阵，字段含 \`analysis_status=not_analyzed\`；dev 结果还明确写入 \`formal_eligible=false\`。它不执行 04/v008 G4 的全文阅读、25篇核心对话或具名研究复核。

**因此：** 即使未来经显式正数配置运行，它也只是独立摘要候选采集；不得把其输出直接等同于正式准入、全文已读或学术审查通过。当前零目标配置必须继续保留。

### 3. v005 production registry 与 04/v008 旧正式路径

\`\`\`text
00/v005/module_registry.json
  └─ module_id=04 → 04_议题文献与现实/v008_第8版
       ├─ manifest entrypoint：tools/research.py
       ├─ research.py：plan / run / execute / validate / export / status / acquire
       ├─ stage04.py + literature_sources.py
       └─ G4：100篇有效摘要 + 25篇核心文献全文完整阅读
             + 来源/证据/关系/路径/现实材料 + 具名质量复核
\`\`\`

- v005 module registry 中 module 04 的路径是 \`04/v008\`，\`optional=false\`、\`execution_scope=research\`。
- v008 manifest 为 \`framework_status=ready\`、\`implementation_status=implemented\`，但 \`business_status=planned\`。它是当前生产注册表指向的旧模块，不代表业务验收已经完成。
- v008 \`research.py\` 是实际 CLI；支持 plan/run/execute/validate/export/status/acquire。
- v008 \`stage04.validate()\` 的 G4 要求摘要目标至少100、核心全文至少25；核对摘要具名阅读记录、全文身份/哈希/完整页范围、核心对话、来源与证据、政策/新闻上下文，并通过 \`signoff()\` 绑定质量复核。返回 \`needs_review\` 或 \`passed\`，同时明确 \`business_quality_automatic=false\`。
- v008 \`literature_sources.DESIGNATED\` 是六刊：\`中国社会科学、社会学研究、探索与争鸣、中国青年研究、经济研究、管理世界\`。它不含《社会》、ASR、AJS。

**因此：** v008 G4 是旧生产注册路线的全文级业务门禁，不能与 v009 的九刊摘要研究门禁混称，也不能声称 04/v012 standalone candidate 已经完成 G4。

## 三、期刊范围与数量合同对照

| 路径 | 期刊范围 | 数量/层级 | 放行/状态 |
|---|---|---|---|
| v009 原 3.x policy | 九刊：七本中文期刊 + ASR + AJS | formal：initial 5 + supplemental 35；dev：5 + 5 | v009 自己的 preliminary/design/final review 与 S08 状态机；当前 v012 strict 固定 dev |
| 04/v012 standalone candidate | 九刊，与 v009 policy 完全一致 | 摘要级；默认 0/0 disabled；显式实验另受 pilot/扩展规则约束 | manifest candidate；不自动进入 v009 review/S08 或 v008 G4 |
| v005 registry → 04/v008 | 六刊；不含《社会》、ASR、AJS | 100篇摘要 + 25篇核心全文 | G4 全文证据与具名研究复核；manifest business_status=planned |
| 11/v007 collector | 本身不固定正式期刊政策；调用方传入 journals/config | 由调用方 policy/config 决定 | 不是独立准入控制器 |

必须区分两个“正式”概念：

- v009 policy 中的 \`formal=5+35\` 是原 3.x staged-topic 的正式模式检索配额；它不是 04/v008 的 100摘要/25全文 G4。
- v012 strict 当前通过 \`original_command(... --mode dev)\` 运行原 v009，所以当前 5.0 strict 路径尚未调用 v009 formal 配额。
- v008 G4 是旧 04 模块自己的全文级质量门禁；它不是 v012 strict 当前状态机的一部分。

## 四、发现的边界与未闭合点

1. **候选与正式路径没有自动桥接。** 04/v012 standalone 输出摘要矩阵；代码没有自动将它转成 v009 的正式 review/S08 回执，也没有自动送入 v008 G4。需要显式交接和重新核验，不能以文件存在替代准入。
2. **六刊与九刊范围不同。** v009/04-v012 candidate 为九刊；04/v008 G4 仅六刊。若把九刊候选结果直接交给 v008，额外的《社会》、ASR、AJS 不属于 v008 的 \`DESIGNATED\`。本任务只记录差异，不擅自扩大旧生产路径名单。
3. **注册不等于业务通过。** v005 registry 仍指向 v008，但其 manifest \`business_status=planned\`；04/v012 则明确是 candidate。两者都不能被描述成已经完成真实生产业务验收。
4. **候选注册链只是路径/依赖兼容。** 04/v012 registry 沿 previous_registry/phase2_registry/base_registry 读取旧注册信息以建立模块路径；这不表示它调用 v005 production module 作为自己的准入器。
5. **policy 的 candidate_registry 指针不是 v009 的动态期刊来源。** v009 当前实际从 \`POLICY["journals"]\` 生成搜索配置；导入 \`native_library.registry()\` 用于模块/schema 路径和候选配置一致性检查。若未来仅修改 policy 中的 candidate_registry 字符串，不会自动改写 registry() 固定读取的候选注册表路径。
6. **strict doctor 的检查粒度较弱。** v012 strict doctor 检查 v009 journals 长度为9，但不逐项比较名称；04/v012 \`native_library.registry()\` 才执行 candidate journals 与 v009 policy 的完整列表相等检查。B16 应统一文档/索引/测试表述，是否增强 strict doctor 另按 B16 实际范围决定。
