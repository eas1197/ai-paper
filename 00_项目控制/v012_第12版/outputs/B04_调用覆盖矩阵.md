1. **已接通的主链：** v012 能调用原 v009 完成初始化、现实观察、解释反诘、议题定位，并把初查交回原 v009 的 `advance/search/receipt`；研究状态、原始检索数量和初查门槛仍由 v009 持有。

4. **调度边界：** autopilot 在 `initial` 调用返回后会停止外层步骤循环；原 v009 的 `advance()` 自身仍可按原规则处理批次、预算和续跑。不能把一次 autopilot 调用误写为整条初查及后续审查已经端到端完成。

## 5. B04b 覆盖范围与权威阶段顺序

本子项只核对原 v009 的审查状态、v012 对审查报告的接收入口，以及 S08 冻结调用。原始流程的关键转移为：

`initial → preliminary_review → (academic_pass → design_review；或满足完整 pass 条件后进入 supplemental) → supplemental → final_review → s08_ready → frozen`

其中：
- 初查达到原定有效题录数量且理论材料非空，原 v009 将状态推进到 `preliminary_review`。
- 初审的 `academic_pass` 只保留学术价值判断，转入 `design_review`；初审若直接给出完整 `pass`，则还必须通过数据可行性与方法路径门禁，之后进入 `supplemental`。
- `design_review` 的 `pass` 也进入 `supplemental`；补查达到原定合并文献目标后进入 `final_review`。
- 最终审查 `pass` 进入 `s08_ready`；只有该状态可调用 `freeze()`，冻结成功后进入 `frozen`。

以上是原 v009 状态机的行为，不是 v012 新增或简化的研究阶段。

## 7. 审查报告接收与独立性边界

1. **v012 有接收入口，不等于有独立审查派发器。** `ai_paper5_strict.py` 的 CLI 有 `review` 子命令，要求 `--run-id` 和 `--report`；主分支将该文件路径传给原 v009 `review` 命令，随后读取更新后的 stage。该路径只负责接收并执行原校验，没有创建 reviewer 会话、分配独立审查者或取得平台签发的 reviewer receipt。
2. **autopilot 的等待是明确的。** 对 `preliminary_review`、`design_review`、`final_review` 等不属于 `PHASES` 的状态，`step()` 返回 `blocked_by_original_v3_gate`，附带原 `prepare` 命令；不会以内部研究会话角色扮演结果推进状态。
3. **原报告字段不是身份凭证。** 原 v009 要求 `model="gpt-6.2-sol"`、非空且不重复的 `invocation_id`、证据哈希、理由和问题；这些只能验证声明字段和输入版本，不能证明报告来自真实独立会话。B03 已将该缺口标为 `not_verified`，B04b 保留此判断。
4. **S08 的自动触发不弥补身份缺口。** 当外部报告被接收后使状态进入 `s08_ready`，下一次运行 autopilot 会走 `status(progress=True)` 并执行 freeze；freeze 没有额外的 reviewer 身份校验。因此，当前代码可证明的是“报告满足原 v009 技术/证据/设计合同后冻结”，不能证明“审查者独立身份已验证后冻结”。
5. **冻结不等于正式资格。** S08 输出固定 `formal_eligible=false`；`frozen` 之后 autopilot 停止并等待 06 材料适足性和 07 写作回执。B04c 负责核对这些下游入口，本子项不提前执行。

## 8. B04b 结论

- **已接：** 原 v009 审查报告接收入口、证据哈希校验、学术/材料路由、补查、最终审查后的 S08 freeze 调用均由 v012 包装并保留原逻辑。
- **未接：** v012 没有自动派发 preliminary/design/final 三类独立学术审查；strict 的 `review --report` 是外部报告接收器，不是审查执行器。
- **人工等待：** preliminary_review、design_review、final_review 均为显式等待节点；操作者需取得报告并手动调用 review。frozen 后的 06 材料适足性与 07 写作回执也仍等待后续阶段。
- **关键风险：** S08 freeze 会在 `s08_ready` 状态由 autopilot/advance 自动触发，但当前 reviewer 身份认证仍为 not_verified。此处是现有代码的真实性边界，不在 B04b 擅自修改。
- **验收口径：** 本子项为静态源码映射任务。阶段、输入、输出、状态转移、调用入口、等待点及身份限制均有直接源码依据，可标记 B04b verified；未运行 CLI、未生成或提交真实 review report、未执行独立审查或研究实验。

## 12. S08 与 06 材料的证据绑定

真正将 S08 与后续定性材料锁定的是原 v009 `question_binding.binding(work, directory)`，调用点在 `resume_writing.resume()`，而不是首次 `qual_materials.py` 采集入口。

`binding()` 的关键核验包括：

1. `staged_topic.json` 必须为 `frozen`；state.question 与 `s08_topic.json.question` 一致。
2. 最后一条原始审查 history 必须为 pass，question 与 S08 一致；其 evidence_sha256 必须与 S08 一致，并重新计算 merged literature、theories 及启用上下文证据的 hash；S08.review_sha256 必须等于该最终报告的 canonical digest。
3. `conversion.new_question` 必须等于 S08.question；`conversion.core_question` 必须等于 `framework.core_question`。
4. 定向材料 receipt 必须属于当前 run，phase 为 `framework_collection`；receipt 中 conversion/framework canonical digest 必须匹配当前文件，events/response SHA-256 必须匹配实际原始文件。
5. 若 receipt 是修复后的子批次，递归核对 parent receipt 文件哈希、材料 ID 集合、added/retired IDs，并确保未修改的旧材料逐项保留。

通过后生成 question_id、semantic_version、method、freeze_sha256、framework_sha256、receipt_sha256 等绑定信息，供后续矩阵/写作使用。

**边界：** 该函数确实能拒绝 S08 问题、冻结审查、conversion、framework 或材料回执之间的不一致；但它只在 `resume-writing` 进入时执行。首次 conversion、初步采集、框架采集和矩阵生成本身并不调用 binding。因此这是**下游强绑定、上游延迟校验**，不能描述成 S08 自动驱动的端到端材料管线。

## 13. 独立适足性、材料修复与经验矩阵的附加门禁

### 13.1 两类 review 不可混用

- `qual_materials.py --review` 写入的 `review.json`：审查转换后的定性问题、方法路径及初步材料搜索回执；通过后状态为 `qualitative_design_ready`。
- `resume_writing.py` 读取的 `matrix_independent_review.json`：审查已生成的经验矩阵；pass 时还必须附带 `material_adequacy`，决定哪些 receipt material IDs 是符合冻结设计的合格事件，以及材料对问题的支持程度。

两者的输入、阶段、输出不同，不能用初步方法可行性通过代替矩阵适足性通过。

### 13.2 material_adequacy 的确定性检查及边界

`writing_material_status()` 要求：
- `eligible_event_ids` 为当前 receipt 中存在、互不重复的 material_id；
- `reason` 非空；
- `support` 只能为 sufficient、insufficient、unknown；
- 没有 eligible ID 时不允许声明 sufficient。

映射结果：sufficient → ready；insufficient → insufficient_core_material；unknown → awaiting_material_adequacy。

该 helper 只检查 ID 唯一性和是否属于当前 receipt，并不自行证明这些 ID 对应不同真实事件，也不判断每条材料是否实质回答研究问题；“合格事件”与支持程度仍依赖独立审查报告的实质判断。若 review 缺 material_adequacy，程序明确等待，不会用材料条数代替适足性。

### 13.3 材料修复的证据连续性

`repair_materials.repair()` 以原 receipt hash、framework hash 和逐条 review item 构成幂等任务键；修复任务只核验审查指出的缺口，限制原生搜索动作预算，要求每条新增/修正材料标记原 issue_index，并通过 supersedes 指明退役的旧 material_id。合并后保留未退役旧材料，记录 added/retired IDs、parent_attempt、parent_receipt_sha256、conversion/framework hash 和 review_key。 `rebind_requirements()` 只允许修正各理论维度的 needed_material 需求，不得改变核心问题、理论上下文或维度推导。

`resume_writing` 在返修后重新构建矩阵、核对完成项并再次派发 reviewer。其内部后续 review dispatch 会通过 Codex CLI 生成 thread_id、events、response hash、usage 和 validated record；这不等于首轮 `matrix_independent_review.json` 已由该入口自动生成。
