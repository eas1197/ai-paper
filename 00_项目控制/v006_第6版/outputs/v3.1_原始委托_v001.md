# 任务：基于 v3.0 真实试跑与学术审计，制定 v3.1 改造方案

你现在需要对自动论文项目的选题流程进行一次系统性改造。



本任务不是简单修复 Bug，而是基于 v3.0 的真实试跑结果，重新审查学术流程、问题演化机制、证据约束和正式交接机制，形成可执行、可验收的 v3.1 改造方案。



**本轮只做审计、设计和任务书编制，不直接修改生产代码，不启用 v3.1，不改变当前生产版本。**

## 二、改造目标

v3.1 的核心目标有四个：

1. 提高研究问题的质量，避免把数据诊断误认为理论创新。
2. 让文献阅读真正参与研究问题的形成，而不是仅仅完成文献数量指标。
3. 保证问题从提出、解释、反问、修正到正式冻结的全过程具有可追溯性。
4. 在不显著增加模型调用和无效工作量的情况下，提高研究判断的可靠性。

特别注意：



不要为了提高系统复杂度而增加不必要的智能体、对话轮次、审批表和重复审查。



优先考虑通过数据结构、流程约束、证据复用和针对性审查解决问题。

## 三、重点改造任务

### P0-01：重新设计研究问题分类体系

目前系统存在主研究问题与测量诊断问题混在同一候选池的问题。



必须设计明确的分类体系，至少区分：

- 主研究问题：具有独立理论或现实研究价值的问题。
- 子研究问题：服务于主问题的具体分析问题。
- 测量诊断：检验变量定义、缺失、测量误差和观测偏差。
- 数据可行性任务：验证问卷、样本、变量和数据是否支持设计。
- 稳健性任务：检验结果对不同设定的敏感性。

明确规定：

1. 只有符合条件的主研究问题才能进入正式候选题池。
2. 测量诊断、数据任务和稳健性任务必须绑定父问题。
3. 不得把同一研究问题的不同测量方案当作多个独立研究方向。
4. 不得通过增加诊断任务数量制造候选问题的多样性。
5. 诊断结果可以促使主问题修改、降级或撤回，但不能自动成为新的理论创新。

设计相应的数据 Schema、ID 关系、状态流转和校验规则。

### P0-02：强化研究问题演化机制

建立完整的问题演化记录。



每次修改问题，必须记录：

- 原始问题；
- 原始理论命题；
- 原始研究范围；
- 修改后的问题；
- 保留了什么；
- 改变了什么；
- 为什么修改；
- 文献依据；
- 新增了什么知识；
- 解决了什么原有问题；
- 是否引入了新的竞争解释；
- 新问题是否仍然具有独立研究价值。

特别增加创新性质判断：

- 理论创新；
- 机制解释创新；
- 研究设计创新；
- 测量创新；
- 经验情境拓展；
- 已有研究的重复验证。

不能将问题变得更具体、样本变得更容易获得或模型变得更容易估计，直接认定为研究创新。



每次问题演化还必须回答：



**如果新旧问题得到不同答案，我们对原有理论或现实判断究竟会有什么不同认识？**



如果无法回答，应降低问题的创新性评价，必要时撤回。

### P0-03：强化 S07 正式反方审查与 G5 冻结之间的强制关系

此前审计发现，正式审查与 G5 冻结之间的约束还不够牢固。



重新设计正式审查凭证机制。



审查通过凭证至少绑定：

- run_id；
- 当前 attempt；
- G4 manifest 哈希；
- 当前研究问题 ID；
- 研究问题版本哈希；
- 审查报告哈希；
- 审查状态；
- 审查时间。

G5 必须验证：

1. G4 当前 attempt 已通过。
2. S07 审查凭证存在。
3. 审查对象与当前研究问题完全一致。
4. 上游 G4 证据包没有变化。
5. 研究问题没有在审查后被修改。
6. 审查结果为正式通过，而非探索性通过。

任何一项不满足，都不得冻结。



允许探索性运行，但探索性运行不能生成正式冻结状态。



同时保留失败记录和反馈路径，不能通过修改状态字段绕过审查。

### P1-01：改进文献阅读与理论解释机制

不要仅仅提取文献中的研究问题、变量和结论。



需要进一步提取：

- 作者试图解释什么现象；
- 作者提出了什么理论命题；
- 作者认为作用机制是什么；
- 机制成立需要什么条件；
- 作者排除了哪些竞争解释；
- 作者的结论适用于什么范围；
- 文章留下了什么尚未解释的问题；
- 不同理论解释会产生什么不同预测。

特别要求：



研究问题必须与已经阅读的核心全文形成实质对话。



不能仅仅通过关键词不同、研究地区不同、样本不同或摘要没有出现某个词，认定研究存在空白。

### P1-02：强化证据定位核验

目前已经能够验证一部分原文短摘、文件哈希和页码，但仍需检查审查过程提交的定位信息是否真正对应原始材料。



设计：

1. evidence_id 与原始文献、文件及页码绑定。
2. 直接证据和推断证据明确区分。
3. 推断证据保留基础证据链。
4. 审查引用的页码、章节和短摘必须能够回溯。
5. 无法自动核验的内容明确进入人工复核状态，不能直接判定通过。

不得为了提高自动化率而降低证据要求。

### P1-03：完善模型调用与成本审计

此前 D08 的内容对照与成本对照存在区别。



需要明确区分：

- 实际模型调用次数；
- 模型名称和版本；
- 输入与输出 Token；
- 实际 API 费用；
- 模型调用失败和重试；
- 模型调用凭证；
- 执行者手工记录的数据。

有提供方原始用量凭证时，使用原始凭证。



没有原始凭证时，标记为未知或人工报告，不得伪装成精确测量。



不得仅凭内容输出相似，就认定某个版本更省额度。



同时考虑预算上限、重复调用识别和已有证据复用，避免重复阅读与重复审查。

### P2-01：设计真实正向验收

当前 v3.0 已经证明了一部分失败拦截能力，但完整正向业务路径尚未充分验收。



v3.1 必须设计一套完整的正向验收：



自主选题 → G4 文献证据 → S07 反方审查 → G5 正式冻结 → 06 数据方法 → 07 写作交接。



验收必须使用真实研究课题和真实证据。



不得通过降低摘要、全文数量要求，伪造文献记录或手工修改状态字段制造通过结果。



如果真实材料不足，应如实报告阻塞点。



还需要保留负向测试：

- G4 未通过；
- 问题版本发生变化；
- 审查凭证过期；
- 上游哈希变化；
- 证据定位失效；
- 审查不通过；
- 诊断任务被误当作主研究问题。

## 六、执行纪律

1. 先审计，后设计。
2. 先确认问题是否真实存在，再提出改造。
3. 不允许为了完成任务而重复创造已经存在的功能。
4. 不允许把提示词约束当成工程强制约束。
5. 不允许把程序运行成功当成研究质量通过。
6. 不允许为了通过验收而降低原有研究标准。
7. 每项改造必须有可检验的验收标准。
8. 每项新增功能必须说明它解决了什么问题，以及是否增加模型消耗。
9. 发现现有设计已经足够的地方，应明确保留，不要为了体现改造工作量而重写。
10. 保留所有历史版本和失败记录。

本轮禁止：

- 修改 v005 生产控制模块；
- 修改现有启用模块；
- 将 v006 标记为生产可用；
- 直接开始 v3.1 编码；
- 擅自修改 G4、G5 的数量门槛；
- 删除历史运行记录；
- 伪造任何测试通过状态。
